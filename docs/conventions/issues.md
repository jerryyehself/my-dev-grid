# 開 issue

寫給開 issue 的人。**一張 issue 就是一張 PR 的範圍。**

## 段落

照下面四段寫，標題文字照抄。還有沒決定的事時，在「要做的事」前面加一段「待決定」；有待決定的 issue 要加 `planning` 標籤，決定之前不動手。

```
## 背景
## 要做的事
## 驗收條件
## 範圍外
```

- **背景**：現況和為什麼要改。指向 repo 裡的檔案或規則（例如 `docs/conventions/security.md`），附上相關的程式片段。不寫只有維護者知道的脈絡。
- **要做的事**：逐點列。要改的檔案寫完整路徑，包含清單類的檔案（例如 `routes/api.php`、`AdminAudit::MODELS`）。
- **驗收條件**：寫成能用指令或請求判斷過不過的條件。行為改動寫出具體的請求跟預期回應（例如 `PUT /api/documentations/1` 送 `url: "data:text/html,…"` → 422，`errors.url` 有值）。最後一條固定寫「`composer test` 在 SQLite 與 PostgreSQL 都通過」；動到 API 文件時，加上「`php artisan scramble:export` 的輸出符合預期」。
- **範圍外**：不能碰的檔案、不能改的 API 形狀。至少寫「上面沒列的檔案」。

## 大小

- 大小看**改動種類**，不看檔案數。一張 issue 只放一種可以單獨審、單獨合併的改動。
- 同一種機械式的改動開一張，不管有幾個檔案：例如把 4 個 FormRequest 的 `url` 規則一起改掉、把 snake_case 方法改名。
- 不同種類的改動分開，例如修 bug 和改名分成兩張。
- 資料庫結構變更要分次部署的（見 [`data.md`](data.md)），每一次部署開一張，前一張部署完才開下一張。
- 不夾帶「順便」的事。想到的另外開，或寫進範圍外。

## 合併還是拆開

| 情況                                           | 做法                                       |
| ---------------------------------------------- | ------------------------------------------ |
| 同一種改法套到多個檔案                         | 一張                                       |
| 兩件事會改到同一個檔案                         | 一張；要分就依序開，前一張合併後才開下一張 |
| 兩件事不共用檔案，各自審、各自合併都不會壞東西 | 分開                                       |
| B 要等 A 做完（或部署完）才能做                | 分開，A 合併後才開 B                       |

- 不要同時開著兩張會改到同一個檔案的 issue。清單類的檔案（`routes/api.php`、`AppServiceProvider`、`composer.json`）最容易互相衝突。
- 引用其他 issue 一律寫編號（`#115`），不寫「前一張驗證那張」。

## 標籤

- 修 bug 加 `bug`，新功能加 `enhancement`，還在討論的加 `planning`。
- 加**剛好一個** `area:` 標籤（`auth`、`api`、`data`、`deploy`、`docs`…，需要時再新增）。

## 標題

- 寫要達成的結果：`建立／更新連結時要檢查兩端實體的分類是否符合述詞的主體／客體`。
- 用繁體中文。檔名、類別名、函式名維持原文。

## 不能寫

這是公開 repo。issue 的內文、標題、留言都不寫：

- 私有文件裡的決策或待辦編號
- 維護者的原話、對話內容
- 私有 repo 的路徑、沙箱的本機路徑
- 密鑰、正式環境的資料（日誌、IP、使用者 id、email）、個人資料
- 雲端帳號的識別碼、告警門檻
- 還沒修好的漏洞細節。這類問題不開 issue，改用 GitHub 的私下回報漏洞功能。

## 要先問維護者的事

登入授權、部署設定（`Dockerfile`、`docker/`、workflow、環境變數）、資料庫結構，屬於 `CLAUDE.md` 定義的高風險改動。這類 issue 可以開，但驗收條件要包含 `CLAUDE.md` 規定 PR 說明要寫的回滾方式與資料安全檢查，合併前也要先問維護者。
